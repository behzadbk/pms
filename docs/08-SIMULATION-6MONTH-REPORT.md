# گزارش شبیه‌سازی ۶ ماهه (نسخه‌ی محلی)

اسکریپت: `tests/sim_6month.py` — روی ۸ سرویس زنده + PostgreSQL 16 + RabbitMQ + Redis اجرا می‌شود.
ساختمان تستِ ۱۲ واحدی را سوپرادمین می‌سازد (کاملاً خام)، و نقش‌های زیر روی API واقعی کار می‌کنند:
سوپرادمین · مدیر · حسابدار · مسئول مشاعات · امنیت · آشپزخانه · ساکن (۵ پروفایل پرداخت: خوش‌حساب، دیرپرداخت، بدهکار، همیشه‌بدهکار، نیمه‌پرداخت).

**گذر زمان:** ساعت سیستم جلو نمی‌رود. ۶ دوره‌ی شارژ (فروردین تا شهریور معادل ۲۰۲۶-۰۴ تا ۲۰۲۶-۰۹) در گذشته صادر می‌شود، پس سررسیدها واقعاً گذشته‌اند و قفل بدهکاری روی ساعت واقعی DB کار می‌کند.
رزرو/مهمان/بسته در ۶ دور اجرا و هر دور ۳۰ روز به گذشته منتقل می‌شود.

> ⚠️ این نتیجه فقط **منطق برنامه** را می‌سنجد. تنظیمات سرور، nginx/SSL، env، SMS/درگاه واقعی، و cron/jobهای ماهانه روی VPS را نمی‌بیند؛ برای آن‌ها تست آنلاین جدا لازم است.

## نتیجه
- قبل از رفع: **۱۶۹ قبول / ۱۶ رد**  ·  بعد از رفع: **۱۷۸ قبول / ۷ رد** (۷ موردِ باقی‌مانده همه تصمیم محصولی/قابلیت جدید هستند، پایین ببینید)
- ایزوله‌سازی بین ساختمان‌ها: همه‌ی بررسی‌ها سالم (RLS، لاگ، مشاعات، قوانین).
- رقابت هم‌زمان رزرو: ۲۵ درخواست هم‌زمان → دقیقاً ۱ موفق، بدون خطای ۵۰۰.
- قفل بدهکاری: درست، شامل مرز مهلت (۲۳ روز تأخیر با مهلت ۲۳ → بسته، ۲۴ → باز) و برداشته‌شدن فوری بعد از تسویه.
- ساختمان تازه واقعاً خام است (هیچ ردیفی در هیچ جدولِ tenant_دار جز حساب مدیر).

## باقی‌مانده (نیاز به تصمیم/قابلیت جدید — در این PR دست نخورده)
1. **ساختمان تازه نمی‌تواند شارژ صادر کند:** API برای ساخت کاربر «حسابدار» و برای تعریف «فرمول شارژ» وجود ندارد (شبیه‌ساز با SQL دور زد). بدون این‌ها ساختمان جدید از پنل کاملاً قابل‌راه‌اندازی نیست. (P1)
2. **ماژول غذا در ساختمان تازه:** endpoint ساخت رستوران/کافه (venue) نیست. (P2)
3. **مشاعات:** API ساخت/ویرایش مشاع `max_hours` و `slot_hours` را نمی‌پذیرد؛ همه‌ی مشاعات یک‌ساعته می‌مانند. (P2)
4. **دیرکرد:** هیچ jobی وضعیت `overdue` نمی‌دهد و ستون `late_fee_amount` هرگز پر نمی‌شود. نیازمند تصمیم درباره‌ی نرخ/قاعده‌ی جریمه. (P2)
5. **`due_date`:** pg ستون DATE را به‌صورت Date در منطقه‌ی زمانی سرور برمی‌گرداند (روی سرور با `TZ=Asia/Tehran`: `2026-04-09T20:30:00.000Z` یعنی یک روز قبل برای کلاینت UTC). پیشنهاد: `types.setTypeParser(1082, v => v)` یا `TZ=UTC` ثابت در compose و ارسال تاریخ ساده. (P2)
6. **رمز اولیه‌ی ساکن = شماره‌ی واحد** (و نام کاربری = موبایل): حدس‌زدنش ساده است. پیشنهاد: رمز تصادفی/کد یک‌بارمصرف. (P2)
7. **سیستم تیکت/CMMS** در بک‌اند نیست (فقط درخواست کودک `ticket`)؛ SPEC آن را دارد. جزو شبیه‌سازی نیامد.
8. معماری هر ساختمان = tenant در یک PostgreSQL مشترک با RLS (نه دیتابیس فیزیکی جدا). اگر «دیتابیس جدا برای هر ساختمان» الزام است، این یک تصمیم معماری است.
