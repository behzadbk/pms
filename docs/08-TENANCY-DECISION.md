# ۰۸ — تصمیم معماری: مدل چندمستأجری (Tenancy)

> وضعیت: **پیشنهاد — تصمیم نهایی با مالک محصول.**
> تاریخ: ۱۴۰۵/۰۷ · دامنه: همه‌ی سرویس‌های بک‌اند (`identity`، `property`، `facility`، `finance`، `guard`، `notification`، `audit`، `fnb`)

## ۱. وضعیت فعلی

هر ساختمان/برج یک **tenant** است (ردیف `identity.tenants`) و همه‌ی tenantها در **یک دیتابیس PostgreSQL مشترک** و یک مجموعه جدول زندگی می‌کنند:

- هر جدول دامنه ستون `tenant_id` دارد و **Row-Level Security** با `FORCE ROW LEVEL SECURITY` روشن است (policy: `tenant_id = platform.current_tenant_id()`).
- سرویس‌ها با نقش `app_user` (بدون `BYPASSRLS`) وصل می‌شوند و هر درخواست داخل `db.withTenant(tenantId, fn)` اجرا می‌شود که `app.current_tenant_id` را با `set_config(..., true)` فقط برای همان تراکنش ست می‌کند.
- کارهای cross-tenant (لاگین با subdomain، پنل سوپرادمین) فقط از `withPlatformAccess` و روی جدول‌های بدون RLS (`identity.tenants`، `platform_admins`، `platform_invoices`) انجام می‌شود؛ شمارنده‌های هر ساختمان در پنل پلتفرم هم با `withTenant` همان ساختمان خوانده می‌شود، نه با دور زدن RLS.

یعنی ایزولاسیون **منطقی** است، نه فیزیکی؛ و پرسش ممیزی این بود که آیا «هر ساختمان یک دیتابیس جدا» درست‌تر نیست.

## ۲. سه گزینه

| معیار | ۱) دیتابیس مشترک + RLS (فعلی) | ۲) schema به‌ازای هر tenant | ۳) دیتابیس به‌ازای هر tenant |
|---|---|---|---|
| **هزینه‌ی زیرساخت** | کمترین؛ یک کلاستر، یک pool، حافظه‌ی مشترک. مناسب صدها ساختمان کوچک | متوسط؛ یک کلاستر ولی catalog سنگین (هزاران جدول/ایندکس به‌ازای هر ساختمان) | بیشترین؛ هر دیتابیس connection pool، حافظه‌ی `shared_buffers`/کش و پروسه‌ی نگهداری (autovacuum) خودش را می‌خواهد |
| **عملیات روزمره** | ساده: یک deploy، یک مانیتورینگ، یک vacuum | سخت‌تر: کار با `search_path` در هر درخواست، pg_dump/ابزارها با هزاران schema کند می‌شوند | سخت: N اتصال/N مانیتورینگ؛ نیاز به orchestration و فهرست مرکزی |
| **ایزولاسیون داده** | منطقی؛ ایمنی وابسته به درست بودن policy و استفاده‌ی همیشگی از `withTenant`. باگ در policy = نشت بین ساختمان‌ها | منطقی-قوی‌تر؛ سطح نقش/دسترسی per-schema ممکن است ولی همان نقش مشترک معمولاً وصل است | قوی‌ترین؛ نشت بین tenantها در سطح SQL ممکن نیست؛ رمز/کلید/رمزنگاری جدا قابل اعمال |
| **Migration** | یک‌بار برای همه؛ ولی تغییر سنگین (ALTER جدول بزرگ) همه را همزمان درگیر می‌کند | N بار اجرا؛ شکست نیمه‌کاره = نسخه‌های ناهمسان | N بار + هماهنگی نسخه؛ rollout تدریجی ممکن (مزیت) ولی پیچیده |
| **Backup/Restore یک ساختمان** | سخت‌ترین بخش: backup فیزیکی همه‌چیز را برمی‌دارد؛ بازیابی تک ساختمان نیاز به export منطقی دارد (این سند: `scripts/export-tenant.sh`) | متوسط: `pg_dump -n schema` | ساده‌ترین: `pg_dump`/snapshot همان دیتابیس؛ PITR مستقل |
| **Noisy neighbour** | بزرگ‌ترین ریسک: یک ساختمان با کوئری سنگین/حجم زیاد روی همه اثر می‌گذارد؛ باید با ایندکس‌های `(tenant_id, …)`، `statement_timeout` و rate-limit مهار شود | مشابه ۱ (منابع مشترک) | ندارد در سطح DB؛ منابع قابل اختصاص |
| **Scale مرتبط با تعداد ساختمان** | عالی (تا ده‌ها هزار tenant) | بد (محدودیت عملی چند هزار schema) | بد (محدودیت عملی صدها دیتابیس در یک کلاستر؛ بیشتر → چند کلاستر) |
| **گزارش‌گیری cross-tenant (پنل SaaS)** | یک کوئری | یک کوئری با UNION یا حلقه | باید روی همه‌ی دیتابیس‌ها حلقه زد یا data warehouse داشت |
| **انطباق/مقررات (مثلاً داده‌ی مشتری سازمانی)** | قابل قبول برای مشتری عمومی؛ مشتری سازمانی ممکن است جدا بخواهد | — | بهترین پاسخ به «داده‌ی ما باید جدا باشد» |

## ۳. تحلیل برای محصول «همین»

- مشتری هدف: **ساختمان‌های مسکونی** (از ۱۰ تا ۵۰۰ واحد). هر ساختمان داده‌ی کمی دارد (چند هزار تا چند ده هزار ردیف). هزینه‌ی یک دیتابیس جدا به‌ازای هر ساختمان در برابر درآمد ماهانه‌ی اشتراک (طبق `tiers.ts`: ۲۵ تا ۶۵ هزار تومان به‌ازای هر واحد) توجیه اقتصادی ندارد.
- بیشتر کار سیستم **تعاملی و کوچک** است (رزرو، شارژ، تیکت)؛ ریسک noisy neighbour در سطح فعلی پایین است و با ایندکس‌های `tenant_id`، `statement_timeout` و محدودسازی نرخ (که الان برای لاگین هم اضافه شده) قابل مهار است.
- بزرگ‌ترین مزیت دیتابیس جدا، **بازیابی تک ساختمان** و **ایزولاسیون برای مشتری حساس** است؛ هر دو را می‌شود بدون بازطراحی با مسیر ارتقای زیر پوشش داد.
- ریسک اصلی مدل فعلی (نشت به‌دلیل فراموش‌شدن `withTenant`) با این‌ها پوشش داده شده: `FORCE RLS`، نقش بدون `BYPASSRLS`، و نبودن هیچ مسیر داده‌ای بدون `withTenant` به‌جز جدول‌های صریحاً «پلتفرمی». پیشنهاد: تست خودکار «کاربر ساختمان A هرگز ردیف B را نمی‌بیند» برای هر جدول جدید در CI.

## ۴. توصیه

**الان: دیتابیس مشترک + RLS (بدون تغییر).** دلایل: هزینه و پیچیدگی عملیاتی کمتر، مهاجرت یک‌باره، مطابق مقیاس بازار هدف. همراه با دو تکمیل که این سند اضافه کرده است:

1. **پشتیبان/خروجی منطقی هر ساختمان** (پیاده‌سازی‌شده): `scripts/export-tenant.sh` و endpoint سوپرادمین `GET /platform/buildings/:id/export`.
2. **مسیر ارتقا** به دیتابیس اختصاصی برای ساختمان‌های پرمصرف/سازمانی (بخش ۵) — بدون بازنویسی سرویس‌ها.

> **تصمیم نهایی با مالک است.** اگر کسب‌وکار قرار است عمدتاً به مشتری سازمانی/دولتی با الزام «داده‌ی جداگانه» بفروشد، گزینه‌ی ۳ باید از ابتدا پیش‌فرض شود و مسیر ۵ همان کار را به‌صورت تدریجی انجام می‌دهد.

## ۵. مسیر ارتقا به دیتابیس اختصاصی (Premium/Enterprise)

مرحله‌ای و برگشت‌پذیر؛ سرویس‌ها فقط یک نقطه‌ی تماس با DB دارند (`DatabaseService.withTenant`) پس تغییر در همان‌جا متمرکز است.

1. **ستون مسیریابی** — migration جدید:
   ```sql
   ALTER TABLE identity.tenants ADD COLUMN IF NOT EXISTS database_url_secret text; -- ارجاع به secret manager، نه رشته‌ی اتصال خام
   ALTER TABLE identity.tenants ADD COLUMN IF NOT EXISTS db_mode text NOT NULL DEFAULT 'shared' CHECK (db_mode IN ('shared','dedicated'));
   ```
2. **Pool lookup در `withTenant`** — کش حافظه‌ای `Map<tenantId, Pool>`؛ اگر `db_mode='dedicated'` از secret خوانده و Pool اختصاصی (`max` کوچک) ساخته شود، وگرنه Pool مشترک. روی دیتابیس اختصاصی `set_config('app.current_tenant_id', …)` باز هم اجرا می‌شود (همان RLS، دفاع عمق؛ و همان کد سرویس‌ها بدون تغییر کار می‌کند). جدول‌های پلتفرمی (`tenants`، `platform_*`) فقط در دیتابیس مرکزی می‌مانند.
3. **ساخت دیتابیس مقصد** — اجرای `db/migrate.sh` روی دیتابیس تازه (همه‌ی migrationها idempotent هستند).
4. **انتقال داده** — `scripts/export-tenant.sh <subdomain>` → وارد کردن CSVها با `\copy ... FROM` در دیتابیس مقصد به ترتیب وابستگی (اسکیماهای `identity`، `property`، `residency`، بقیه). پنجره‌ی نگهداری کوتاه: ساختمان را `suspended` کنید، export بگیرید، import، تأیید تعداد ردیف‌ها با `manifest.json`، سپس `db_mode='dedicated'`.
5. **Rollback** — تا قبل از پاک‌کردن داده‌ی قدیمی، برگرداندن `db_mode='shared'` کافی است. داده‌ی ساختمان از دیتابیس مشترک فقط پس از یک دوره‌ی اطمینان حذف شود.
6. **Migration آینده** — `db/migrate.sh` باید روی همه‌ی دیتابیس‌های `dedicated` (فهرست از `identity.tenants`) هم اجرا شود.

## ۶. پشتیبان‌گیری و بازیابی یک ساختمان

**خروجی:** 
```bash
scripts/export-tenant.sh borj-aftab            # → export-borj-aftab-YYYYMMDD-HHMMSS.tar.gz
# یا از پنل: سوپرادمین ← مجتمع‌ها ← «خروجی داده» (JSON)  |  GET /identity/platform/buildings/:id/export
```
محتوا: `schema.sql`، `data/<schema>.<table>.csv` برای هر جدول دارای `tenant_id`، `tenant.csv`، `manifest.json` (تعداد ردیف هر جدول). اسکریپت با نقش `app_user` و داخل تراکنشی که `app.current_tenant_id` را ست کرده اجرا می‌شود؛ یعنی COPY از RLS عبور می‌کند و حتی با اشتباه در `WHERE` داده‌ی ساختمان دیگری وارد خروجی نمی‌شود. هش رمزها، توکن‌های دعوت و PIN خروج در خروجی نیستند.

**بازیابی (در دیتابیس تازه):** `db/migrate.sh` → درج ردیف `tenant.csv` → `\copy <table> FROM 'data/<table>.csv' CSV HEADER` به ترتیب وابستگی (`identity.users` → `property.*` → `residency.*` → بقیه) → مقایسه با `manifest.json`. کاربران باید رمز را از مسیر «فراموشی/ارسال دعوت مجدد» دوباره تنظیم کنند (هش رمز عمداً صادر نمی‌شود).

**محدودیت‌ها:** این backup منطقی است و جایگزین backup فیزیکی/PITR کل کلاستر نیست؛ هر دو باید باشند. فایل‌های آپلودی (اگر خارج از DB ذخیره شوند) جدا هستند.
