# اصلاحات پنل مدیر ساختمان + نقش حسابداری (۲ مهر ۱۴۰۵)

بر اساس تست محلی پنل مدیر ساختمان. همه‌ی موارد زیر پیاده‌سازی و با مرورگر واقعی (Chromium) تست شد — ۳۶ سناریو، همه سبز.

## ۱. قوانین رزرو هوشمند مشاعات — قابل ویرایش شد

| قبل | بعد |
|---|---|
| قوانین ثابت بود و آیکون تنظیمات کاری نمی‌کرد | دکمه‌های **مشاع جدید**، **ویرایش** و **حذف** |

- فرم ویرایش: نام، نوع، ظرفیت، رنگ در تقویم، نیاز به تایید مدیر، سقف رزرو هر واحد (در روز/هفته/ماه)، حداقل/حداکثر فاصله تا رزرو، طول بازه، مهلت کنسلی، بیعانه و سیاست بازگشت آن.
- سانس‌بندی هفتگی (مردانه/زنانه/خانوادگی/آزاد) با افزودن و حذف ردیف.
- صفحه‌ی رزرو ساکن هم از همین قوانین می‌خواند، پس تغییر مدیر فوراً روی رزرو ساکنین اعمال می‌شود.

## ۲. رزرو مشاعات

- **ثبت دستی رزرو (هماهنگی تلفنی):** مشاع، واحد، نام و شماره تماس، تاریخ، بازه‌ی ساعت و یادداشت. رزرو مستقیم «تاییدشده» ثبت می‌شود و برای همان واحد اعلان داخل برنامه می‌رود.
- **عدم تایید با دلیل:** کنار «تایید» دکمه‌ی «عدم تایید» اضافه شد. دیالوگ آن چند دلیل آماده دارد (مثلاً «سقف رزرو ماهانه تکمیل شده») و متن آزاد هم می‌پذیرد. دلیل برای ساکن اعلان می‌شود و در «رزروهای من» هم دیده می‌شود.
- فیلتر لیست: در انتظار / ثبت دستی / همه.

## ۳. اعلانات و رأی‌گیری

- دکمه‌ی **اعلان جدید** و **نظرسنجی جدید** حالا فرم باز می‌کنند.
- **فرم‌ساز نظرسنجی:** چند سؤال، هر سؤال با تعداد دلخواه گزینه (افزودن/حذف)، تک‌گزینه‌ای یا چندگزینه‌ای، مهلت شرکت، وزن‌دهی بر اساس متراژ.
- **مخاطبان:** همه‌ی ساکنین، فقط مالکین، فقط مستأجرین، پرسنل/استف، نگهبانی، حسابداری، بخش‌های تعریف‌شده (بلوک A/B/C)، و واحدهای مشخص (مثلاً «۴، ۷، ۱۲»).
- پس از انتشار، برای مخاطبان **اعلان داخل برنامه** ارسال می‌شود. زنگوله‌ی بالای صفحه حالا واقعی است: شمارنده‌ی خوانده‌نشده، لیست اعلان‌ها و رفتن به صفحه‌ی مربوطه.
- صفحه‌ی جدید **اعلانات و نظرسنجی** برای ساکن، پرسنل، نگهبانی و حسابداری. هر کس فقط موارد مخصوص خودش را می‌بیند و می‌تواند یک بار رأی بدهد. پس از رأی، نتیجه نمایش داده می‌شود.

## ۴. تیکت‌ها — جزئیات + تشخیص هوشمند تجهیز

- با زدن روی هر تیکت، جزئیات کامل آن باز می‌شود: متن، گزارش‌دهنده، زمان، روند پیگیری، یادداشت و تغییر وضعیت (تغییر وضعیت برای ساکن اعلان می‌شود).
- **تشخیص هوشمند:** نوع خرابی از روی کلیدواژه‌های متن تیکت تشخیص داده می‌شود (آسانسور، روشنایی/لامپ، لوله‌کشی، موتورخانه، اطفای حریق، برق، درب). بعد تجهیز دقیق بر اساس نام و محل پیدا می‌شود. مثلاً «آسانسور B» از «آسانسور A» جدا تشخیص داده می‌شود.
- **آخرین سرویس/تعویض** همان تجهیز با تاریخ و «چند روز پیش» نمایش داده می‌شود. اگر موعد سرویس دوره‌ای گذشته باشد، هشدار قرمز هم دیده می‌شود.
- **سابقه‌ی کامل تجهیز:** همه‌ی سرویس‌ها و تعمیرهای قبلی و تیکت‌های قبلی همان تجهیز در همان پنجره دیده می‌شوند.
- **ثبت تعمیر / تعویض / سرویس / بازدید** از داخل تیکت: تاریخ، شرح، انجام‌دهنده و هزینه. به‌صورت اختیاری تیکت هم بسته می‌شود.
- **اگر سابقه‌ای نبود:** اگر تجهیز قبلاً تعریف نشده بود، از همان تیکت تعریف می‌شود (یا هنگام ثبت اولین تعمیر خودکار ساخته می‌شود). از دفعه‌ی بعد، تاریخ آخرین تعویض آن نمایش داده می‌شود.

## ۵. مالی — جدا شدن حسابداری از مدیریت

نقش جدید **حسابداری (`accountant`)** اضافه شد.

| پنل | دسترسی |
|---|---|
| **حسابداری** `/accountant` | داشبورد مالی · **شارژ و مطالبات** (فرمول، پیش‌نمایش، صدور و اعلان به ساکنین، ثبت وصول، ویرایش، جریمه) · **صندوق و فاکتورها** (ثبت فاکتور با اقلام، پیوست تصویر، ثبت پرداخت، حذف، گردش صندوق) |
| **مدیر ساختمان** `/admin/finance` | **فقط گزارش:** خلاصه‌ی مالی، لیست فاکتورها با فیلتر دسته و **جزئیات هر فاکتور**، وضعیت وصول شارژ هر دوره |

- «شارژ و مطالبات» و «صندوق و فاکتورها» از منوی مدیر حذف شدند. به‌جای آن‌ها «گزارش مالی» آمد. آدرس قدیمی `/admin/charges` به گزارش شارژ هدایت می‌شود.
- بک‌اند: `AppRole` در هر ۸ سرویس `accountant` را می‌شناسد. `POST /charges/generate-monthly` حالا `@Roles('accountant')` است و برای مدیر 403 برمی‌گرداند.
- دیتابیس: مایگریشن `backend/identity-service/prisma/migrations/003_accountant_role.sql` (idempotent) نقش را به CHECK constraint اضافه می‌کند. `seed-dev.sql` کاربر `accountant@borj-aftab.test` / `Passw0rd!` را می‌سازد.

## ذخیره‌ی داده — مهم

API بک‌اند برای اعلانات، تیکت، دارایی‌ها/سابقه‌ی سرویس، فاکتور و رزرو دستی هنوز ساخته نشده است (در فهرست «گام‌های بعدی» README). به همین دلیل همه‌ی این فرم‌ها فعلاً روی یک استور مشترک سمت کلاینت کار می‌کنند (`frontend/src/lib/store.ts`):

- داده در `localStorage` همان مرورگر ذخیره می‌شود و با رفرش از بین نمی‌رود.
- بین تب‌ها همگام است: اگر مدیر در یک تب اعلان منتشر کند، زنگوله‌ی ساکن در تب دیگر همان لحظه به‌روز می‌شود.
- **بین دو دستگاه یا دو کاربر مختلف مشترک نیست.** برای استفاده‌ی واقعی چندکاربره باید اکشن‌های `store.ts` به endpointهای بک‌اند وصل شوند. امضای اکشن‌ها (`publishAnnouncement`، `decideReservation`، `addInvoice`، `addServiceRecord`، …) طوری نوشته شده که فقط بدنه‌شان با `fetch` عوض شود.
- برگرداندن داده‌ی نمونه: در کنسول مرورگر `localStorage.removeItem('hamin.demo-store')` و بعد رفرش صفحه.

## نحوه‌ی تست

```bash
git pull
cd db && ./migrate.sh --seed      # مایگریشن 003 + کاربر حسابدار
cd ../frontend && npm install && npm run dev
```

ورود حسابدار: مجتمع `borj-aftab` · `accountant@borj-aftab.test` · `Passw0rd!`
